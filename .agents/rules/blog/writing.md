# AI Mind 博客写作规范

## 1. 适用范围

这份规范用于以下场景：

- 版本博客起稿
- 博客提纲整理
- 博客成稿扩写
- 博客发布前润色
- release 对外短文案整理

## 2. 规则来源与合并结论

这份规范整合自以下来源：

- 历史博客规则草稿
- `.agents/rules/blog/prompt-template.md`
- 既有版本博客的稳定写法
- 当前项目新增的博客写作要求

合并结论：

- **没有硬冲突，可以保留并统一收口**
- 既有规则强调的是：`AI Mind` 博客不是普通教程文，而是版本演进记录与工程复盘
- 新增规则强调的是：要照顾第一次看到该项目的读者、风格更偏掘金成稿、口吻更统一、结尾更完整

因此最终统一定位为：

> `AI Mind` 的博客是一种“版本演进记录 + 工程复盘 + 轻教学表达”的技术文章。

它不是：

- 纯教程照抄文
- 产品宣传稿
- 只有变更清单的版本日志

## 3. 文章定位

每篇博客都应优先回答这些问题：

1. 这一版为什么值得单独写
2. 这一版解决了什么工程问题
3. 为什么这样设计，而不是别的方式
4. 本版做了哪些取舍、保留了哪些边界
5. 这版对后续 `Skill / MCP / Agent / 数据层` 演进留下了什么空间

## 4. 目标读者与阅读视角

默认读者不是只关注版本更新的人，还包括：

- 第一次读到这篇博客的人
- 第一次知道 `AI Mind` 这个项目的人
- 正在做 AI Native / Runtime / Tool Calling / MCP / Agent 工程的人

写作时必须优先照顾“第一次阅读该篇博客、第一次接触该项目”的视角。

具体要求：

- 开头前 5 到 8 段内，要让读者知道项目背景、本版主题、为什么值得单独写
- 不要默认读者已经了解前几个版本
- 不要上来就堆版本细节或文件名
- 章节之间要尽量顺着陌生读者的认知路径展开

## 5. 开头规则

每篇博客开头都应尽量包含这几个元素：

1. 当前版本锚点
2. 项目背景简介
3. 这篇文章真正要讨论的问题
4. 一句可提前收住全文的核心判断
5. 一处图片占位

开头必须找合适位置介绍项目背景，并预留一处前端展示或结构示意图。

推荐顺序：

1. 抛出一个真实工程问题
2. 说明这篇对应哪个版本
3. 用 1 到 2 段介绍项目背景
4. 落到本版主题
5. 给出“先看结论”
6. 放图片占位

图片占位默认优先级：

- 项目主界面 / 前端展示图
- 主链结构图
- 核心能力效果图

如果暂时没有图片，也必须保留占位，不要直接删掉。

## 6. 结构习惯

推荐结构保持以下节奏：

- 背景与问题
- 本版目标 / 本次要回答的问题
- 总体方案 / 结构链路
- 核心模块设计
- 关键实现细节
- 踩坑与修正
- 当前结果与边界
- 下一步方向
- 项目地址 / Star 引导 / 后续路线

说明：

- 结构可以按版本主题调整
- 但不建议缺少“背景、取舍、边界、下一步、项目地址”这些关键块

## 7. 口吻与风格

### 7.1 口吻

默认多使用：

- 我
- 我们

尽量少使用：

- 你
- 你们

例外：

- 标题中的反问句
- 少量面向读者的自然引导句

### 7.2 风格

整体风格要求：

- 偏掘金风格
- 有结论感
- 有问题感
- 有真实工程取舍
- 有一点教学风，但不要太重
- 保持“实战 + 教学”兼具，以实战复盘为主

不建议写成：

- 概念大全
- 协议百科
- 纯配置说明书
- 只有自我感受、没有工程判断的随笔

## 8. 文件名、模块名与代码说明规则

为了让读者更容易读懂文章，对于首次出现的重要文件名、模块名、目录名，都要补充职责说明。

推荐格式：

- `chat-orchestrator`（聊天主链的阶段编排和策略判断）
- `chat-session`（按请求组装模型上下文、messages 和 active tools）
- `tool-runtime`（工具校验、执行与展示映射）

适用对象：

- 文件名
- 目录名
- 包名
- 模块名
- 导出入口

原则：

- 如果读者只看名字无法理解职责，就必须补括号说明
- 如果一组文件是同一层职责，也可以直接写成“名称 + 括号说明”的列表

## 9. 图片与代码规则

### 9.1 图片

- 如果涉及图片，先写图片占位，不编造图片链接
- 开头至少保留 1 处图片占位
- 图片说明要写清这张图要表达什么

### 9.2 代码

- 代码只放少量关键片段，不堆砌
- 优先讲最能体现方案价值的 4 到 8 段代码
- 每段关键代码前，先说“这段代码解决了什么问题”
- 每段关键代码后，解释关键逻辑、边界条件或设计意义
- 不要贴长代码而不解释

## 10. 结尾规则

每篇博客结尾必须包含：

1. GitHub 地址
2. 轻量 Star 引导
3. 1 到 2 句后续路线说明

默认项目地址：

- GitHub：
  [https://github.com/HWYD/ai-mind](https://github.com/HWYD/ai-mind)

系列博客固定入口：

- 掘金专栏：
  [https://juejin.cn/column/7619152366395195401](https://juejin.cn/column/7619152366395195401)

说明：

- GitHub 地址是正文结尾必须出现的固定项
- 掘金专栏入口属于长期固定入口，优先长期保留在 `README.md`
- 如果正文结尾需要，也可以视情况补充专栏入口

推荐结尾语气：

- 自然
- 轻量
- 像系列更新的尾声

不建议：

- 过强营销感
- 连续多句重复导流

## 11. 成稿优化规则

在整理和润色博客时，必须额外检查这些点：

- 是否有重复性叙事
- 是否对第一次阅读该篇博客的人足够友好
- 是否有太重的方案文档口吻
- 是否把“为什么这样设计”讲清楚了
- 是否把“当前没有做什么”讲清楚了
- 是否让文件名、模块名足够可读
- 是否在开头尽快把读者带进项目语境

默认优化原则：

- 少重复同一句判断
- 少“这一节要讲什么”这类元叙述
- 多直接写结论、判断和取舍
- 尽量从陌生读者的视角顺一遍

## 12. 与项目文档的关系

写博客前优先参考：

- `README.md`
- 最新版本的 `specs/`
- 相关 `docs/adr/`
- 相关 `docs/architecture/`
- 相关 `docs/versions/` 和 `docs/releases/`
- 相关历史博客
- `private-folder/` 草稿素材仅在用户明确要求或需要回看历史推演时参考

博客应该能和这些文档互相印证，而不是各说各话。

## 13. 一句话总原则

每篇博客都要尽量做到：

- 陌生读者能看懂
- 老读者能看到版本判断
- 工程读者能看到真实取舍
- 整体读起来像一篇可直接发掘金的成稿
