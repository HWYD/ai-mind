你现在是我的技术博客合作者，请基于以下要求，为当前项目版本生成一篇适合发布到掘金风格平台的中文技术博客。

使用这份模板前，先同步参考：

- `.agents/rules/blog/writing.md`
- `.agents/rules/blog/review-checklist.md`
- 当前版本对应的 `specs/`
- 相关 `docs/adr/`、`docs/architecture/`、`docs/versions/`、`docs/releases/`

## 一、写作目标

请围绕本次版本迭代的方案设计、实现过程、关键取舍、踩坑经验和最终结果，写出一篇“既能讲清楚思路，也能体现工程实践价值”的技术博客。

整体风格要求：

- 参考技术博客网站“稀土掘金”常见文章风格：标题明确、开头抓人、结构清楚、强调问题背景、方案设计、关键实现、经验总结。
- 如用户明确要求，可参考 `private-folder/blogs` 下的历史博客风格；不要把 `private-folder/` 草稿内容当作当前实现事实源。
- 文风自然、专业、有个人思考，避免空话、套话、营销腔。
- 不要写成产品宣传稿，要写成真实的工程实践总结。

## 二、你的任务分两步

### 第一步：先输出详细博客提纲

在正式写正文前，先输出一版“详细博客提纲”，要求：

- 提纲必须细到二级或三级标题。
- 每个章节下面要简要说明这一节准备讲什么。
- 如果博客中需要图片展示，请先进行占位处理，在提纲和正文里都明确写出图片占位说明。
- 在开头合适位置预留“项目效果图/页面截图/运行截图”的展示位。
- 在需要讲实现细节的章节里，明确标出哪些地方需要插入关键代码片段。
- 在结尾部分预留 GitHub 仓库地址与 Star 引导位。

### 第二步：根据提纲输出完整正文

等我确认后，再按确认过的提纲输出完整博客正文。

## 三、正文内容要求

请围绕以下信息写作：

- 项目名称：`[在这里填写项目名]`
- 当前版本：`[例如 v0.0.6]`
- 本次主题：`[例如 多 Tool Runtime 初步扩展 / Tool Calling 工程化 / 聊天主链路重构]`
- 本次目标：`[在这里填写本次迭代要解决的问题]`
- 技术栈：`[在这里填写，例如 Next.js + React + LangChain.js + Ollama + Zod + Tailwind CSS]`
- 目标读者：`[例如 正在做 AI Native 应用、Agent、Tool Calling、本地 LLM 工程化的人]`

正文必须满足下面这些要求：

1. 标题要像一篇真正会发到掘金的文章

- 要具体，不要空泛。
- 最好能体现“我做了什么”“解决了什么问题”“为什么值得看”。

2. 开头要有吸引力

- 先讲这次迭代想解决什么问题。
- 讲清楚为什么这个问题值得单独做一版。
- 不要一上来就堆技术名词。

3. 开头合适位置预留图片展示位

- 明确写出：
    - `> 图片占位 1：项目主界面截图`
    - `> 图片占位 2：关键功能效果图`
    - `> 图片占位 3：核心流程/运行结果图`
- 如果本次版本不需要 3 张图，可按实际删减，但至少预留 1 处效果图位置。
- 如果暂时没有现成图片，不要跳过图片说明，仍然保留占位文字，方便后续人工补图。

4. 要讲清楚“为什么这样设计”

- 不只是讲做了什么。
- 还要讲为什么这么做，而不是别的做法。
- 必要时要写出取舍，例如：
    - 为什么先做最小可行闭环
    - 为什么这样拆模块
    - 为什么这样设计协议/数据结构
    - 为什么暂时不做某些能力

5. 对必要关键代码进行阐述

- 不是简单贴代码。
- 要选最关键、最能体现方案价值的代码片段来讲。
- 每段关键代码前，先用一句话总结“这段代码的作用是什么”。
- 每段代码前要先说明它解决了什么问题。
- 每段代码后要解释关键逻辑、边界条件或设计意义。
- 如果代码较长，只截取必要部分，避免大段无解释代码堆砌。

建议优先讲解这类代码：

- 关键数据结构
- 核心主链路/编排逻辑
- Tool/模块注册与执行逻辑
- 前后端协议或流式处理逻辑
- 参数校验、归一化、容错处理
- 体现设计取舍的代码

6. 文章结构建议尽量接近下面的节奏

- 背景与问题
- 本次版本想解决什么
- 总体方案/架构图/链路图
- 核心模块设计
- 关键实现细节
- 踩坑与修正
- 当前结果与边界
- 下一步计划
- 结尾总结

7. 内容要有“真实工程感”

- 可以写踩坑。
- 可以写中间推翻过的方案。
- 可以写验证后发现的问题。
- 可以写当前版本刻意保留的边界。
- 让读者感受到这不是拼凑文章，而是实际做过、想过、权衡过。

8. 结尾必须预留 GitHub 地址和 Star 引导

- 结尾加一节“项目地址”或“结语”。
- 预留类似下面的内容：

```md
## 项目地址

GitHub：
[这里替换成仓库地址]

如果这篇文章或这个项目对你有帮助，欢迎点个 Star 支持一下。
```

- 语气自然，不要太生硬。

## 四、写作格式要求

- 使用 Markdown 输出。
- 标题层级清晰，合理使用 `##`、`###`。
- 适当使用列表，但不要全篇都是列表。
- 关键链路可以用代码块或文本流程图表示。
- 如果文章里有图片展示需求，一律先使用“图片占位”文本，不要擅自编造图片内容或图片链接。
- 如果涉及架构流程，可优先使用这种简洁文本图：

```text
用户输入
  -> 前端页面
    -> /api/chat
      -> runtime / orchestrator
        -> tool calling / model
          -> 返回流式结果
```

- 如果适合，也可以插入少量“关键代码”代码块。
- 不要生成表情符号。
- 不要生成过度夸张的标题党表达。

## 五、输出约束

- 先只输出“详细提纲”，不要直接输出全文。
- 提纲确认后，再输出完整正文。
- 正文长度要足够支撑一篇完整技术博客，但不要写成流水账。
- 如果某些信息不足，请先根据上下文做合理补全，并在文中保持一致。

## 七、输出示例风格要求

请尽量写出这样的感觉：

- 像一个真的做了这次迭代的人在复盘
- 不是单纯罗列“我用了什么技术”
- 更强调“为什么这样设计、这样做带来了什么、踩了哪些坑”
- 兼顾可读性和技术密度

现在请先输出：

## 推荐补充提示

如果你希望 AI 更稳定地产出你要的风格，可以在上面提示词后面继续追加这段：

```md
补充要求：

1. 如果文章里要放代码，请优先选择最关键的 5 到 10 段代码，不要堆太多。
2. 每段关键代码都要解释“它解决了什么问题”。
3. 每段关键代码前，先写一句“这段代码的作用”。
4. 每一节都尽量回答“为什么要这样设计”。
5. 如果本次版本有明显踩坑，请单独成节说明。
6. 文章结尾要自然收束到项目演进路线和 GitHub 地址。
7. 文章要保留工程思考，不要写成教程照抄文。
```
