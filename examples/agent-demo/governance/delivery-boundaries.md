# Delivery Boundaries (交付边界规则)

版本: v1.0  
日期: 2026-07-01  
适用范围: Delivery Chain 所有交付活动

## 总览

本文档定义了 Delivery Chain 的交付边界规则，用于确保交付过程中的范围控制、资源隔离和安全合规。所有交付活动必须严格遵守这些边界。

---

## 1. 范围边界 (Scope Boundaries)

### 1.1 允许的交付范围

✅ **只允许交付以下内容**：

1. **Demo 场景优化**
    - examples/agent-demo/scenarios/ 目录下的场景优化
    - 新的 demo 场景添加
    - 现有场景的改进和标准化

2. **评分标准完善**
    - examples/agent-demo/rubrics/ 目录下的评分标准
    - 评分维度的调整和优化
    - 评分细则的补充和完善

3. **治理规则更新**
    - examples/agent-demo/governance/ 目录下的规则
    - 交付边界规则的更新
    - 工程规则的更新

4. **文档改进**
    - 现有文档的纠错和完善
    - 新文档的添加（仅限 demo 相关）
    - README 的更新

### 1.2 禁止的交付范围

❌ **严格禁止以下交付**：

1. **核心代码修改**
    - 不得修改 apps/webapp/ 下的核心业务代码
    - 不得修改 packages/ 下的核心库代码
    - 不得修改协议定义

2. **新功能开发**
    - 不得开发新的业务功能
    - 不得添加新的 API 端点
    - 不得修改现有的功能逻辑

3. **架构变更**
    - 不得修改整体架构
    - 不得修改模块划分
    - 不得添加新的依赖

4. **数据库变更**
    - 不得修改数据库 schema
    - 不得添加新的数据库表
    - 不得修改数据迁移脚本

5. **第三方依赖变更**
    - 不得添加新的 npm 依赖
    - 不得升级现有依赖版本
    - 不得移除现有依赖

### 1.3 范围变更流程

如需扩大交付范围，必须：

1. 提交正式的范围变更请求
2. 说明变更的原因和必要性
3. 评估变更的风险和影响
4. 获得技术负责人和安全负责人的双重批准
5. 更新本文档并记录变更

## 2. 资源边界 (Resource Boundaries)

### 2.1 允许访问的资源

✅ **只允许访问以下资源**：

1. **文件系统资源**
    - examples/agent-demo/ 目录及其子目录
    - 只读访问，不得修改其他目录的文件

2. **配置资源**
    - examples/agent-demo/ 下的配置文件
    - 只允许读取，不允许修改项目根配置

3. **测试资源**
    - examples/agent-demo/ 下的测试数据
    - 测试用例和测试脚本

### 2.2 禁止访问的资源

❌ **严格禁止访问以下资源**：

1. **源代码目录**
    - apps/ 目录
    - packages/ 目录
    - lib/ 目录
    - src/ 目录

2. **配置文件**
    - 项目根目录的 .env\* 文件
    - 任何包含密钥、密码、令牌的配置文件
    - 数据库配置文件

3. **敏感数据**
    - 用户数据
    - 日志文件（可能包含敏感信息）
    - 构建产物
    - Git 历史和元数据

4. **系统资源**
    - 环境变量
    - 进程信息
    - 网络连接
    - 文件系统其他部分

### 2.3 资源访问原则

1. **最小权限原则**
    - 只授予完成任务所需的最小权限
    - 默认只读，写权限需要单独申请

2. **白名单原则**
    - 只允许明确列出的资源
    - 其他资源默认禁止访问

3. **审计原则**
    - 所有资源访问必须可审计
    - 异常访问必须有日志记录

## 3. 安全边界 (Security Boundaries)

### 3.1 代码安全

✅ **必须遵守**：

1. **输入验证**
    - 所有外部输入必须验证
    - 路径必须规范化后验证
    - 防止路径遍历攻击

2. **输出编码**
    - 所有输出必须适当编码
    - 防止 XSS 攻击
    - 防止命令注入

3. **错误处理**
    - 错误信息必须脱敏
    - 不得泄露内部实现细节
    - 不得泄露堆栈跟踪

4. **日志安全**
    - 日志不得包含敏感信息
    - 日志不得包含用户数据
    - 日志不得包含密钥或令牌

❌ **严格禁止**：

- 使用 eval() 或类似的动态代码执行
- 使用 any 类型绕过类型检查
- 硬编码密钥、密码、令牌
- 在代码中留下调试语句（console.log 等）

### 3.2 依赖安全

✅ **必须遵守**：

1. **依赖白名单**
    - 只能使用项目现有的依赖
    - 不得添加新的依赖
    - 不得升级依赖版本

2. **依赖审计**
    - 使用现有依赖前必须确认没有已知漏洞
    - 如有漏洞，必须使用替代方案
    - 不得使用有安全风险的依赖功能

❌ **严格禁止**：

- 从不可信源加载依赖
- 动态加载依赖
- 执行外部命令或脚本
- 访问网络资源（除非在白名单中）

### 3.3 数据安全

✅ **必须遵守**：

1. **数据隔离**
    - Demo 数据必须与真实数据完全隔离
    - 不得使用真实用户数据作为 demo 数据
    - Demo 数据不得包含敏感信息

2. **数据脱敏**
    - 所有示例数据必须脱敏
    - 不得使用真实的个人信息
    - 不得使用真实的业务数据

❌ **严格禁止**：

- 访问或使用真实用户数据
- 存储或处理敏感信息
- 发送数据到外部系统
- 持久化任何 demo 数据（除非明确允许）

## 4. 架构边界 (Architecture Boundaries)

### 4.1 允许的架构变更

✅ **只允许以下架构变更**：

1. **纯文档变更**
    - Markdown 文档的添加和修改
    - 文档结构的调整
    - 示例代码的更新

2. **测试代码变更**
    - 测试用例的添加和修改
    - 测试工具的配置更新
    - 测试数据的更新

### 4.2 禁止的架构变更

❌ **严格禁止以下架构变更**：

1. **核心架构变更**
    - 不得修改模块划分
    - 不得修改依赖关系
    - 不得修改接口定义

2. **协议变更**
    - 不得修改 API 协议
    - 不得修改数据格式
    - 不得修改序列化方式

3. **部署变更**
    - 不得修改部署流程
    - 不得修改基础设施
    - 不得修改 CI/CD 配置

## 5. 测试边界 (Testing Boundaries)

### 5.1 允许的测试活动

✅ **只允许以下测试活动**：

1. **单元测试**
    - 测试示例代码
    - 测试工具函数
    - 测试验证逻辑

2. **文档测试**
    - 验证文档示例的正确性
    - 验证代码片段的可执行性
    - 测试文档链接的有效性

3. **静态检查**
    - 代码风格检查
    - 类型检查
    - 拼写检查

### 5.2 禁止的测试活动

❌ **严格禁止以下测试活动**：

1. **集成测试**
    - 不得测试与其他模块的集成
    - 不得测试与外部系统的集成

2. **性能测试**
    - 不得进行负载测试
    - 不得进行压力测试
    - 不得进行基准测试（除非明确允许）

3. **生产环境测试**
    - 不得在生产环境运行任何测试
    - 不得使用生产数据进行测试

## 6. 边界违规处理

### 6.1 违规检测

边界违规通过以下方式检测：

1. **代码审查**：所有变更必须经过严格的代码审查
2. **自动化检查**：通过 CI/CD 管道进行自动化检查
3. **静态分析**：使用静态分析工具检测潜在违规
4. **定期审计**：定期对交付内容进行审计

### 6.2 违规等级

根据严重程度，边界违规分为以下等级：

| 等级     | 描述                             | 示例                       |
| -------- | -------------------------------- | -------------------------- |
| Critical | 严重安全违规，可能导致安全漏洞   | 访问敏感数据、执行外部命令 |
| High     | 严重范围违规，可能影响系统稳定性 | 修改核心代码、添加新依赖   |
| Medium   | 中等范围违规，可能影响功能       | 修改配置、修改测试框架     |
| Low      | 轻微范围违规，不影响核心功能     | 文档格式问题、注释错误     |

### 6.3 违规处理流程

1. **发现违规**：任何人发现边界违规都应该立即报告
2. **评估影响**：技术负责人和安全负责人评估违规的影响
3. **立即回滚**：对于 Critical 和 High 等级的违规，立即回滚变更
4. **根因分析**：分析违规发生的原因
5. **改进措施**：制定并执行改进措施
6. **记录归档**：将违规事件和处理结果记录归档

### 6.4 预防措施

为了预防边界违规，采取以下措施：

1. **明确文档**：确保所有边界规则清晰明确
2. **培训教育**：所有参与人员必须了解边界规则
3. **自动化检查**：在 CI/CD 中添加边界检查
4. **代码审查**：所有变更必须经过严格审查
5. **定期审计**：定期检查边界合规情况

---

## 7. 边界例外处理

### 7.1 例外申请流程

在特殊情况下，如果确实需要突破边界，必须遵循以下流程：

1. **提交申请**：提交正式的边界例外申请
2. **说明理由**：详细说明突破边界的必要性
3. **风险评估**：进行全面的风险评估
4. **影响分析**：分析对系统的影响
5. **多重审批**：获得技术负责人、安全负责人、产品负责人的批准
6. **记录归档**：将申请和审批结果记录归档
7. **限时有效**：例外只在指定时间范围内有效

### 7.2 例外原则

- **例外必须是真正的例外**，不能成为常态
- **例外必须有明确的时间限制**，到期后必须恢复原有边界
- **例外必须有明确的范围限制**，不得扩大范围
- **例外必须有补偿措施**，降低安全风险
