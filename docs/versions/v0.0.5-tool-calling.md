# v0.0.5 Tool Calling

## Summary

`v0.0.5` 在 `v0.0.4` 的本地聊天闭环基础上，加入最小 Tool Calling 实践。

本版本只接入一个工具：`calculator`。重点不是计算器本身，而是验证模型发起 tool call、服务端校验并执行工具、工具结果回填模型、前端结构化展示结果这一整条链路是否成立。

## Goals

- 跑通单 Tool Calling 最小闭环。
- 保持现有 `LangChain.js + Ollama + typed parts + Streamdown` 架构不被推翻。
- 让模型在有工具可用时能够选择是否调用工具。
- 用 `Zod` 校验模型生成的工具参数。
- 在前端展示 `reasoning / tool / text` 三类 part。
- 为多 Tool Runtime 预留 registry 结构。

## Non-goals

- 不做多工具调度。
- 不做多轮 Agent loop。
- 不做工具权限系统。
- 不做工具管理 UI。
- 不做工具结果持久化。
- 不引入 LangGraph 或完整 Agent 框架。

## Key Changes

### 单 Tool 闭环

当前只注册 `calculator`。

服务端在有可用工具时使用模型绑定工具能力；如果模型返回 `tool_calls`，runtime 会校验参数、执行工具、回填 ToolMessage，再生成最终答案。

### 工具参数校验

模型生成的 tool call 不是可信输入。

执行前会经过：

- 工具是否存在检查。
- 参数归一化。
- `Zod.safeParse` 校验。
- 工具执行。

校验失败时输出结构化 tool error，而不是直接让请求崩掉。

### Tool Part 展示

assistant 消息正式支持 `tool` part。

前端不再把工具结果塞进一整段文本，而是能区分：

- reasoning part。
- tool part。
- text part。

### 确定性结果策略

`calculator` 是确定性工具，工具结果比模型二次口算更可信。

因此版本中引入了“确定性工具结果优先”的判断，为后续 authoritative answer 策略打基础。

## Important Interface Changes

- `ChatStreamChunk` 增加 tool 相关事件。
- `MindMessagePart` 增加 `tool` 类型。
- Tool definition 包含 `name`、`schema`、`normalizeArgs`、`formatInput`、`resultIsAuthoritative` 等信息。
- Runtime 开始面向工具定义执行，而不是直接把工具逻辑写死在主链路中。

## Test Plan

- 验证普通问答在工具已绑定时仍可直接回答。
- 验证 `calculator` 可以处理典型计算表达式。
- 验证工具参数非法时输出结构化 tool error。
- 验证工具执行失败不会污染下一轮对话。
- 验证前端可展示 reasoning、tool、text 三类 part。
- 更详细工程验证记录：待补充。

## Result / Outcome

`v0.0.5` 让项目从“只有模型回答”升级为“模型可以发起 Tool Calls，Runtime 可以校验和执行工具，前端可以结构化展示结果”的最小闭环。

这为后续多 Tool Runtime 打下了基础。
