# AI Mind v0.3.0: Tasklist Agent HITL Checkpoint Resume MVP

## Summary

v0.3.0 是 AI Mind Tasklist Agent 的首个 Human-in-the-loop + durable resume 版本。

它只作用于：

```text
/tasklist + @docs://versions/*.md
```

本版的目标不是把 AI Mind 扩展成通用审批平台，而是在当前受控单 Agent 基础上，验证一条更完整、但仍然收敛的业务链路：

- `TasklistStrategy` 生成后必须经过人工审核。
- 只有真正需要修订 tasklist 时，才进入第二个 HITL 审核点。
- tasklist 修订最多执行两轮，避免无限 revise。
- Agent 能在暂停后基于 durable checkpoint 从同一 thread 恢复。
- 恢复后的流继续写入原 assistant message，而不是创建一条新消息。

一句话说，本版验证的是：

> 受控 Tasklist Agent 能不能在关键节点停下来等人确认，并在确认后继续往下走，同时保持 Graph Runtime、stream protocol 和前端消息模型仍然可解释、可观察、可收口。

## Background

在 v0.2.3 中，`/tasklist + @docs://versions/*.md` 已经固定走 LangGraph Graph Runtime，legacy runner、runtime selector 和 fallback 不再参与生产执行路径。

在 v0.2.4 中，Tasklist Agent 又进一步收口为 GraphState 单事实源：graph nodes 直接读取 GraphState 分区、返回 GraphState patch，旧 AgentState adapter 退出生产主链。

这意味着，到 v0.3.0 开始前，Tasklist Agent 已经具备两个重要前提：

- 生产执行路径已经稳定收口到单一 Graph Runtime。
- 内部运行态已经稳定收口到单一 GraphState 模型。

但它仍然是单次 HTTP 请求内完成整条 graph 执行的模型：

```text
POST /api/chat
  -> ChatOrchestrator
  -> runVersionPlanTasklistGraph()
  -> graph.invoke(initialState)
  -> final / stopped / failed
```

此前的 checkpoint 主要是 memory 级别，只适合开发期展示或本请求内调试，不适合作为跨请求恢复能力。

因此 v0.3.0 要补齐的是：

- 人工审核节点。
- durable checkpoint。
- 业务级 run / interrupt 状态。
- resume API。
- 同消息续写的前端协议。

同时仍然保持本版是“受控单 Agent 的演进”，而不是迈向通用 Agent 平台。

## Goals

- Strategy Review 必停。
- Strategy Review 支持 `approve / edit / reject / respond`。
- 第二次 Strategy Review 不再允许 `respond`。
- Tasklist Revision Review 只在 `warningDisposition.fixNow.length > 0` 时出现。
- Tasklist Revision Review 支持 `approve / edit / reject / respond`。
- tasklist 最多两轮受控修订，即最多到 `v3`。
- 引入 PostgreSQL 持久化 AgentRun / AgentInterrupt。
- 引入 LangGraph Postgres checkpointer 支持 durable resume。
- resume 继续更新原 assistant message。
- 普通聊天、Skill、Tool Calling、MCP 不受影响。

## Runtime Flow

本版的生产主流程可以概括为：

```text
readVersionPlan
  -> evaluatePlanReadiness
  -> planningDecision
  -> readOptionalContext?
  -> decideTasklistStrategy
  -> reviewTasklistStrategy              必停
  -> draftTasklistV1
  -> validateTasklistV1
  -> decideWarningDispositionV1
  -> reviewTasklistRevision?             仅当 fixNow.length > 0
  -> revise / validate / revise / validate
  -> final / blocked / rejected
```

更细一点的分支规则是：

```text
decideTasklistStrategy
  -> reviewTasklistStrategy
  -> routeAfterStrategyReview
     - approve / edit -> draftTasklistV1
     - respond -> regenerateStrategyOnce -> reviewTasklistStrategy
     - reject -> stop

draftTasklistV1
  -> validateTasklistV1
  -> decideWarningDispositionV1
     - fixNow.length === 0 -> final
     - fixNow.length > 0 -> reviewTasklistRevision

reviewTasklistRevision
  -> routeAfterTasklistRevisionReview
     - approve -> reviseTasklistV2
     - respond -> reviseTasklistV2
     - edit -> applyEditedTasklistV2
     - reject -> stop

v2
  -> validateTasklistV2
  -> decideWarningDispositionV2
     - fixNow.length === 0 -> final
     - fixNow.length > 0 -> reviseTasklistV3

v3
  -> validateTasklistV3
  -> final or blocked
```

这里最重要的业务语义有两个：

第一，Strategy Review 每次正常生成 strategy 后都必须暂停。

第二，第二个审核点不是“每个 draft 都必停”，而是“只有在真正需要修订时，才请求一次人工授权”。

## Strategy Review

Strategy Review 是本版固定引入的第一个人工审核点。

它支持四种决策：

```text
approve
edit
reject
respond
```

语义分别是：

- `approve`：确认当前 strategy，继续生成 tasklist。
- `edit`：用户通过结构化表单修改 strategy，再基于修改后的 strategy 继续。
- `reject`：停止本轮 Agent，不输出最终 tasklist artifact。
- `respond`：用户补充反馈，允许重新生成一次 strategy，然后再次进入审核。

为了避免无限循环，`respond` 只允许触发一次。第二轮 Strategy Review 仍然允许用户：

```text
approve / edit / reject
```

但不再允许继续 `respond`。

## Tasklist Revision Review

第二个审核点的正式名称是：

```text
Tasklist Revision Review
```

它不是“最终草稿审批”，而是“修订前授权”。

触发条件只有一个：

```text
warningDisposition.fixNow.length > 0
```

也就是说，不是所有 warning 都会触发人工审核。只有当系统明确判断“这次必须立即修”的问题存在时，才要求用户决定是否继续修订。

它支持：

```text
approve
edit
reject
respond
```

语义是：

- `approve`：授权模型按 `fixNow` 执行第一次修订。
- `edit`：用户直接编辑 Markdown，作为第一次修订。
- `reject`：结束本轮，不输出最终 artifact。
- `respond`：用户补充修订要求，后端结合 `fixNow + feedback` 执行第一次修订。

这个审核点每个 run 最多只出现一次。原因是本版希望把“是否继续修订”的决策点压缩到第一次修订之前，第二次修订如果仍然需要，则自动执行，不再重复打断用户。

## Revision Budget

v0.3.0 把 tasklist 修订预算固定为：

```text
maxDraftRevisions = 2
```

也就是：

```text
v1 -> v2 -> v3
```

不允许生成 `v4`。

所有 `v1` 之后的变更都占用这个预算：

- 用户 `edit` 一次，记作一次修订。
- `approve` 触发模型 revise，记作一次修订。
- `respond` 触发模型 revise，也记作一次修订。
- 如果 `v2` 后仍然存在必须立即修复的问题，系统自动执行 `v3`，记作第二次修订。

两轮修订后如果仍然无法通过结构质量门，本版不会继续循环，而是收口为：

- run 已完成。
- 结果状态为 `blocked`。
- 仍然输出当前 artifact，但明确提示不建议直接采用。

## Strategy Contract

为了让前端表单、GraphState patch、planner 输出和 resume decision 能使用同一套结构，v0.3.0 固定 `TasklistStrategy` 为一组枚举化字段：

```ts
export type TasklistStrategyGranularity = 'coarse' | 'medium' | 'detailed'

export type TasklistStrategyStepCountRange = '3-5' | '5-8' | '8-12'

export type TasklistStrategyGrouping = 'by_phase' | 'by_module' | 'by_risk' | 'by_test_flow'

export type TasklistStrategyPriorityFocus =
    | 'core_runtime'
    | 'state_model'
    | 'frontend_ui'
    | 'tests'
    | 'docs'
    | 'deployment'
    | 'compatibility'

export interface TasklistStrategy {
    granularity: TasklistStrategyGranularity
    stepCountRange: TasklistStrategyStepCountRange
    grouping: TasklistStrategyGrouping
    priorityFocus: TasklistStrategyPriorityFocus[]
    notes?: string
}
```

它的设计重点不是“字段越多越好”，而是让 strategy 既稳定、可编辑，又能真实影响 draft 生成：

- `granularity`：控制拆分粗细。
- `stepCountRange`：控制步骤数量区间。
- `grouping`：控制任务分组方式。
- `priorityFocus`：控制强调的实现重点。
- `notes`：承接补充约束，但不回到自由文本 strategy 的旧模式。

## Persistence

v0.3.0 正式引入 PostgreSQL。

Prisma schema 不再放在 `apps/webapp` 私有目录内，而是上移到共享 package，供 webapp 和未来 `project-assistant-service` 共用：

```text
packages/database
```

本版的业务状态表核心是：

- `agent_runs`
- `agent_interrupts`

职责边界很明确：

- `agent_runs`：记录一次 Agent 业务运行的生命周期、所属 session、版本信息、threadId 和结果状态。
- `agent_interrupts`：记录某次人工中断点的 payload、允许决策、当前状态和最终决策。

而 LangGraph Postgres checkpointer 负责的是另一层职责：

- 保存 graph resume 所需的技术状态。
- 支撑同一 thread 的 checkpoint 恢复。
- 不直接对外承担业务 run 查询。

换句话说，checkpoint 不是 AgentRun 的替代品，AgentRun 也不保存完整 GraphState 或 raw checkpoint。

## API and Resume

本版新增一个明确的 resume 入口：

```text
POST /api/agent-runs/:runId/resume
```

它接收：

```ts
{
    interruptId: string
    decision: StrategyReviewDecision | TasklistRevisionReviewDecision
}
```

resume 之前必须校验：

- run 是否存在。
- run 是否属于当前 session。
- run 是否仍处于 paused。
- interrupt 是否仍为 pending。
- 当前 `agentVersion / graphVersion` 是否匹配。
- decision 是否符合对应 schema。

同一次 interrupt 只能被成功消费一次，因此 duplicate resume 必须 fail closed，而不是静默重试。

## Stream and Message Model

为了让 resume 后继续写入原消息，本版新增两个 stream chunk：

```text
agent-interrupt
agent-resume
```

它们的作用分别是：

- `agent-interrupt`：把当前 assistant message 标记为 `paused`，并附带当前 pending review 的公开 payload。
- `agent-resume`：告诉前端“接下来继续往原 assistant message 里写”，而不是新开一条 assistant message。

因此 v0.3.0 的消息状态模型增加了：

```text
streaming
paused
resuming
completed
failed
```

这件事很关键，因为本版的产品目标之一就是：

```text
首次执行 -> 暂停
用户决策 -> 恢复
后续 graph / text / artifact chunk 继续追加到原消息
```

而不是：

```text
暂停时一条消息
恢复时再新开一条消息
```

## UI

本版 HITL 的前端主交互放在输入框上方，而不是塞进消息正文里。

布局职责是：

```text
MessageList
  - AgentTracePanel
  - AgentTextArtifactPanel

ComposerArea
  - HumanReviewComposerPanel
  - ChatComposer
```

这样做的原因是：

- AgentTracePanel 继续负责“过程可观察”。
- HumanReviewComposerPanel 只负责“当前人工决策入口”。
- ChatComposer 继续保持普通聊天输入职责。

当存在 pending interrupt 时：

- 普通 Composer 会被锁定。
- 用户不能通过普通输入框绕过审核卡提交反馈。
- 人工 `respond` 必须走审核卡内部 textarea，并提交到 resume API。

另外，v0.3.0 明确不支持“刷新后自动恢复 pending HITL card”。刷新后用户需要重新发起 `/tasklist`。这不是遗漏，而是本版有意保留的边界：在没有完整恢复原 assistant message、trace 和 artifact 上下文能力前，只拉起一张孤立审核卡会让体验和状态都变得不可靠。

## Boundaries

本版最重要的边界有几条：

- HITL 只作用于 Tasklist Agent。
- 不扩展到普通聊天、reader-skill、utility-skill、MCP、通用 Tool Calling 或其他 Agent。
- review node 本身必须无副作用：不调用模型、不调用工具、不读写数据库、不写文件。
- GraphState 继续保持 JSON-serializable，不放 model、request、writer、AbortSignal、raw Error 或 API key。
- stream、artifact、AgentTracePanel 和已有 chunk 协议保持兼容。

## Non-goals

v0.3.0 不做：

- 通用审批系统。
- Run History。
- Trace replay。
- time travel。
- 任意节点暂停。
- 任意 GraphState 编辑。
- 多人审批。
- 多 Agent 编排。
- 通用 Tool 审批。
- checkpoint migration。
- 跨版本 checkpoint resume。
- 刷新后恢复 pending HITL。

## Verification

本版已完成的工程验证包括：

- database generate / validate / tests。
- webapp tests / typecheck / lint / build。
- stream-core tests / typecheck / build。
- Docker build。
- 容器内 migration / checkpointer setup。
- Docker webapp health / page smoke。

浏览器级的 HITL 分支 smoke 在当前自动化环境下被内置浏览器安全策略阻止访问本机 `127.0.0.1:3000`，因此需要人工复验。

## Final Shape

v0.3.0 收口后的 Tasklist Agent 形态可以概括为：

```text
Strategy 必审
修订前条件式 HITL
最多两轮受控修订
Prisma AgentRun / AgentInterrupt
Postgres durable checkpoint
同 thread resume
原 assistant message 续写
刷新不恢复 pending HITL
受控单 Agent 边界保持
```

这意味着，AI Mind 仍然不是通用 Agent 平台，但它已经向前跨出了一步：不仅能跑一条受控 graph，还能在业务关键节点把“人”的决策正式纳入运行时结构里。
