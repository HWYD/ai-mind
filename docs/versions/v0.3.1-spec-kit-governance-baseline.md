# AI Mind v0.3.1: Spec Kit Governance Baseline

## 摘要

v0.3.1 是 AI Mind 的治理基线版本，不新增业务功能。

它把 v0.3.0 HITL Checkpoint Resume MVP 中已经验证过的工程纪律沉淀为一套面向后续 AI coding 的规格驱动流程：

```text
constitution -> spec -> plan -> tasks -> acceptance -> decisions -> ADR -> implementation review
```

这版不修改 Tasklist Agent Runtime、不修改 Graph、不修改数据库、不修改 stream 协议，也不改变前端交互。

## 为什么需要这个版本

v0.3.0 已经把 Tasklist Agent 推进到带 HITL、durable checkpoint、AgentRun 业务状态和同消息 resume 的阶段。这个阶段之后，AI Mind 的风险不再只是“某个函数写错”，而是更容易出现：

- Agent 边界被无意扩大。
- GraphState、AgentRun、checkpoint 职责混淆。
- stream 协议为了新需求泄露运行时内部细节。
- 数据层或部署脚本发生变化但文档没有同步。
- Codex 执行一个版本时，plan、tasklist、README、release 和真实代码各说各话。

v0.3.1 解决的是这些治理问题。

## 本版变化

- 新增 `.specify/memory/constitution.md`，记录 AI Mind 长期工程原则。
- 新增 `specs/030-tasklist-agent-hitl-checkpoint-resume/`，把 v0.3.0 作为已发布 baseline 沉淀下来。
- 新增 `specs/031-spec-kit-governance-baseline/`，记录本治理版本的 spec / plan / tasks / acceptance / decisions。
- 新增 `docs/adr/`，包含 ADR 模板和首批五个核心架构决策。
- 新增 `docs/architecture/ai-coding-workflow.md`，定义 Change Level A/B/C/D 和 Codex 执行规则。
- 新增 `docs/architecture/spec-driven-development.md`，说明 AI Mind 的本地 Spec Kit 风格流程。
- 新增 `docs/architecture/tasklist-agent-runtime-boundaries.md`，记录 v0.3.0 后 Tasklist Agent 的稳定边界。
- 新增 `.github/pull_request_template.md`，把 constitution check、spec drift check 和 verification 放进 PR 流程。
- 为 Level C / D 引入 clarify、checklist、analyze 质量闸门；小改和普通模块改动不强制执行，避免流程变成负担。

## 非目标

v0.3.1 不做：

- 不修改 runtime。
- 不修改 Tasklist Agent Graph。
- 不修改 Prisma schema。
- 不修改 PostgresSaver。
- 不修改 stream chunk 协议。
- 不修改 API route。
- 不修改前端 reducer 或 HITL UI。
- 不实现 pending HITL recovery。
- 不实现 Run History、Time Travel、事件回放或 `agent_run_events`。

## 后续版本如何复用

小改可以继续轻量推进，但需要说明范围和验证。

跨边界改动，例如 GraphState、stream protocol、Prisma schema、AgentRun 状态、API contract、CheckpointerProvider 或 HITL 行为变化，必须从完整 spec / plan / tasks 开始，并检查 constitution；实现前还要完成 clarify、checklist、analyze 或人工等价检查。

架构级改动，例如 Agent 边界、数据层职责、runtime 主链、checkpoint/resume 语义、部署拓扑或新 service 接入，必须新增或更新 ADR，并把这些质量闸门的结果纳入 review。

## 价值

v0.3.1 让 AI Mind 后续版本不只依赖“人记得边界”，而是让 Codex 和 reviewer 都能先读到同一套事实：

- 什么长期不能轻易改变。
- 当前版本具体要做什么。
- 哪些事明确不做。
- 哪些改动会触发 spec drift。
- 哪些验证是必须的。

这对 AI Mind 作为 Agent 工程化项目尤其重要，因为 Agent、Graph、stream、数据库和前端状态一旦跨层演进，最容易出问题的地方往往不是代码量，而是边界感。
