# v0.0.11 Capability Skill 与 Remote MCP

## Summary

`v0.0.11` 基于 `v0.0.10` 已经稳定的 runtime 边界，补齐 Skill 消费能力所需的 Capability Surface。

核心判断是：Tool、Resource、Prompt 应该能通过统一 capability model 被描述，但三者不需要被强行合并成同一条执行链。Capability Model 统一的是描述层，不是执行链。

本版本也新增了单个 remote MCP service，用于验证 remote capability 最小闭环。它是 mock 远程能力来源，不是完整远程业务平台。

## Goals

- 保持现有 `chat-service facade -> runtime -> stream-core` 边界稳定。
- 建立统一 capability model，覆盖 `tool`、`resource`、`prompt`。
- 增加结构化 Skill metadata，用于 routing 辅助、自描述和前端展示。
- 让 Prompt 成为 Tool / Resource 之外的一等 capability。
- 增加单个 remote MCP server，验证 remote Resource、Prompt、Tool 消费链路。
- 让 capability metadata 进入 runtime 消费链路，而不是只用于展示。
- 在前端流中展示 Skill 命中、capability 类型、来源、位置、server、状态和错误。

## Non-goals

- 不重写 chat runtime。
- 不做 workflow engine。
- 不做 Agent。
- 不做多 remote server 编排。
- 不展开普通业务 API。
- 不做 OAuth 系统。
- 不接数据库。
- 不接第三方 API。
- 不做任意文件系统访问。
- 不强行统一 Tool、Resource、Prompt 的执行语义。

## Key Changes

### Capability Model

Capability model 用稳定方式描述“一个能力是什么”。

第一版覆盖：

- `tool`
- `resource`
- `prompt`

关键字段包括：

- `capabilityId`
- `name`
- `capabilityType`
- `providerKind`
- `location`
- `serverId`
- `title`
- `description`
- `availability`

这个模型可以避免 internal、local MCP、remote MCP 来源中的同名能力互相冲突。

### Skill Metadata

`SkillDefinition` 现在包含 `skillId`、`name`、`description`、`triggerExamples`、`sourceKinds`、`capabilitySelectors` 和 `fallbackPolicy` 等结构化字段。

这些 metadata 是 Skill 的表面，用于 routing、展示和 runtime capability selection。它不承担 workflow 或 Agent planner 职责。

### Prompt 成为一等 capability

Prompt 被加入 capability 类型，而不是隐藏在 Tool 行为里。

本版本包含：

- Local Prompt：`local-file-summary`。
- Remote Prompt：`tasklist-draft`。

Prompt 执行表示 runtime 获取 prompt messages，注入受控参数，再把这些 messages 作为后续模型上下文。它不是 Tool call。

### Remote MCP 最小闭环

Remote MCP 验证使用一个独立 app：`apps/project-assistant-service`。

它对外暴露每类一个 mock remote capability：

- Resource：`project://latest-context`。
- Prompt：`tasklist-draft`。
- Tool：`check_doc_consistency`。

服务使用 Streamable HTTP 和 mock Bearer 鉴权，所有 capability 数据均为 mock。

### Runtime Capability 消费

Runtime 为 `reader-skill` 增加最小 capability 消费层。

它可以解析并执行本版本固定的 remote capability，向流中写出 Resource / Prompt / Tool 执行事实，并把返回结果注入最终回答上下文。

这不是通用 planner，而是一个很窄的 runtime bridge，用于证明 capability metadata 可以被 runtime 消费。

### 前端执行事实

流式协议现在可以表达：

- Skill 命中。
- Prompt 开始与结束。
- Tool、Resource、Prompt 执行事实。
- 来源、位置、server、状态和错误信息。

这让前端具备理解本轮回答发生了什么的技术完整性，同时不把 UI 扩展成复杂调试控制台。

## Important Interface Changes

- Capability 类型包含 `tool`、`resource`、`prompt`。
- Capability provider kind 包含 `internal` 和 `mcp`。
- Capability location 包含 `local` 和 `remote`。
- Skill definition 增加结构化 metadata 与 capability selectors。
- MCP server definition 可以描述本地 `stdio` 和 remote Streamable HTTP server。
- 流式协议支持 `skill-selected`、`prompt-start`、`prompt-end`。
- 流式错误码增加 MCP 相关错误，例如 unauthorized、forbidden、not found、timeout 和 execution failure。

## Test Plan

- 验证 internal tools 可以映射为 capability。
- 验证 local MCP Tool 和 Resource 仍然可用。
- 验证 local Prompt `local-file-summary` 可以被消费。
- 验证 remote Resource `project://latest-context` 可以被消费。
- 验证 remote Prompt `tasklist-draft` 可以被消费。
- 验证 remote Tool `check_doc_consistency` 可以被消费。
- 验证 capability 失败会进入统一流式错误协议。
- 验证普通聊天在未命中 Skill 场景时仍然直答。
- 验证前端消息 parts 可以展示 Skill、Tool、Resource、Prompt、source、location 和 server 信息。

## Result / Outcome

`v0.0.11` 证明了 Skill 可以稳定消费 Tool、Resource、Prompt 组成的 Capability Surface。

它也证明了 remote MCP 可以通过小而明确的 mock 闭环进入项目，而不需要提前把 runtime 推向 Agent、workflow 或平台化方向。
